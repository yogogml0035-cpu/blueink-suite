# 条件化记忆

收到老师反馈后读这里。判断某条记忆能否自动参与写作时读这里。

核心结论：**系统学习的是条件化判断，不是不断增长的规则清单。**


## 一 · 老师的修改稿要登记

修改稿以文件形式给出时，用 `open --mode 学习 --attach <修改稿绝对路径>` 登记，再启动反馈归因员。

理由不是流程完整性：**归因的全部重量都压在"这确实是他改的那一版"上面。** 稿件文件事后被覆盖、改名或移走是常态，而一条记忆的置信度会随着后续证据一路累积——半年后发现某条记忆归因错了，要能回去确认当时比对的到底是哪一版。登记记的是路径、内容哈希和"老师显式提供"这个出处；哈希是这三样里唯一事后无法伪造的。

登记过的修改稿在审计 A2 里合法，即使它不在绑定知识库内——老师的稿子放在哪是他的事。

## 二 · 为什么不能是规则清单

规则清单的失败模式是可预测的：

- 它只增不减。没人敢删，因为每条都来自一次真实的批评。
- 越长越没人看。包括模型——规则挤在同一个上下文里，越靠后越失效。
- 最后每条规则都在某些场合是错的，而系统无法判断"这次算不算"。

于是产生一个荒谬结果：系统积累得越多，表现越不稳定。

条件化记忆携带**触发条件**和**不适用范围**，因此可以被判断；携带**置信度**和**反例**，因此可以被修正。

## 三 · 四级状态

| 级别 | 影响范围 | 进入条件 | 谁批准 |
|---|---|---|---|
| `session` 本次调整 | 只影响当前这一稿 | 老师随口的一次性要求 | 无需批准 |
| `personal` 个人有效知识 | 这位老师以后负责该品牌的任务 | 老师明确说"以后都这样"；或系统从多个独立任务中发现同一规律 | 展示适用条件后老师确认一次 |
| `brand` 品牌候选规律 | 该品牌工作空间内 | 反映品牌／客户稳定偏好，而非个人习惯 | 重复出现且无强反例后晋级，仍需确认 |
| `methodology` 方法论候选 | 可能影响所有品牌与所有老师 | 反馈指向核心编排或通用判断 | **只记录，绝不自动改写通用方法论** |

`methodology` 级的变更必须经过专门的对照验证和对抗审查，由维护者手工执行。**任何工作空间都不允许自动修改 `SKILL.md`、`references/`、`agents/`。**

## 四 · 证据强度

| 证据形态 | 强度 | 初始置信度 | 能断言什么 |
|---|---|---|---|
| 老师明确说明修改原因 | high | 0.50 | 可断言原因，可推出适用条件 |
| 老师在 A/B 之间做了选择 | medium | 0.35 | 可断言方向偏好（他选了哪个变量），不能断言原因 |
| 只有初稿与修改稿，没有理由 | low | 0.20 | **只能记录变化本身**，不许推测动机 |

第三类最容易出错。看到老师把长句改短，写"老师偏好简洁表达"是编造——他可能只是这次篇幅超了。正确的记录是："第 2 段由 68 字改为 41 字，未说明原因。"

## 五 · 置信度怎么变

```
新证据同向、且来自独立任务   →  +0.15（上限 0.9）
新证据同向、但同一任务内     →  +0.05
出现反例                     →  -0.25，并优先考虑缩小适用范围
老师明确否定这条记忆         →  置 0.0，标记 retired，保留记录
连续 6 个月未被命中           →  -0.10（衰减，每次索引时结算一次）
```

四条纪律：

- **上限 0.9，永不到 1.0。** 任何记忆都可能在下一个场景里失效。留出这 0.1 是为了让系统永远保持"这条也许不适用"的可能性。一个饱和到 1.0 的置信度会让"再来一个反例"失去意义。
- **"独立任务"指不同的传播事件。** 同一场活动的三篇稿子里出现三次同向修改，算一次证据，不算三次。这条不加限制的话，一场大活动就能把一条偶发偏好推到高置信度。
- **独立任务必须指向一次真实运行。** `reinforce` 声明为独立事件时会校验 `--run` 对应的运行记录是否存在，不存在就拒绝。允许引用不存在的运行，等于允许凭空制造"多个独立任务中重复出现"——而置信度完全依赖这个计数。同一场活动内的同向修改用 `--same-event`（只 +0.05）。
- **反例不删旧结论。** 降低置信度，或给旧结论加一条"不适用于……"。冲突通常说明适用条件写得太宽，而不是原来的观察是假的。

## 六 · 每条记忆都记归属的老师

学习的对象是"**这位老师**在什么条件下通常如何判断"，不是"这个品牌该怎么写"。所以每条记忆都带 `teacher` 字段，取自工作空间绑定的那位老师。

不记名的后果不是丢信息，是**学出一个不存在的平均人**：同一个品牌可能由两位老师分别负责不同稿件，两个人的偏好混在一条置信度上，表现出来就是"我的偏好时灵时不灵"——最难查的一类问题，因为每一条记忆单看都成立。

- `memory list` 默认只列当前工作空间登记的那位老师的记忆；发现库里有别人的记忆会明确报出来，而不是静默过滤。
- 审计 A6 在同一记忆库里发现两个署名时直接判违约。
- v1 老工作空间迁上来的记忆标成"未记名"，不算混人，但 `doctor` 会持续提示补 `--teacher`。
- 换人就换项目。`bind` 检测到老师改变会拒绝，除非 `--force`。

## 七 · 按置信度使用

| 置信度 | 使用方式 |
|---|---|
| ≥ 0.65 高 | 可自动进入本次写作程序，**但必须在决策卡中可见、可取消** |
| 0.35 — 0.65 中 | 只作推荐或 A/B 备选，不直接控制正文 |
| < 0.35 低 | 只作研究线索，不影响正式生成 |

高置信度记忆参与写作时，决策卡里必须出现它，并写明触发条件：

```
本次采用的条件化知识
2. 媒体供稿中把技术参数转换为可感知场景（置信度 0.72，依据 4 次独立任务）——可取消
```

老师说"取消第 2 项"，本次不启用，并记一次弱反例（-0.10，不是 -0.25：取消可能只是这次不合适）。

## 八 · 一条合格的记忆长什么样

不合格：

> 不要在开头写行业背景。

问题在于它没有触发条件，会被到处滥用；也没有不适用范围，无法判断"这次算不算"。

合格：

> 当媒体供稿需要强化体验感、且参考稿采用第一人称观察时，把技术参数转换为可感知场景；新闻通稿和核心信息文件不适用。

存储形态（`.blueink/learning/memory.json` 中的一条）：

```json
{
  "id": "M-2026-08-22-01",
  "scope": "personal",
  "teacher": "张老师",
  "knowledge": "当媒体供稿需要强化体验感、且参考稿采用第一人称观察时，把技术参数转换为可感知场景",
  "trigger": {"brand": "理想汽车", "category": "媒体观点供稿", "scene": "试驾体验", "publisher": "品牌官方"},
  "not_applicable": ["新闻稿", "核心信息"],
  "evidence": [
    {"run_id": "20260710-...", "strength": "high", "before": "...", "after": "...", "reason": "老师原话"},
    {"run_id": "20260802-...", "strength": "medium", "ab_choice": "b", "variable": "切口"}
  ],
  "evidence_count": 2,
  "distinct_events": 2,
  "counterexamples": [{"run_id": "20260815-...", "note": "核心信息稿中老师要求保留原始参数"}],
  "confidence": 0.5,
  "status": "active | pending_confirmation | retired",
  "created": "2026-08-22",
  "updated": "2026-08-22"
}
```

`distinct_events` 与 `evidence_count` 分开记，因为置信度按前者结算。

```bash
python3 scripts/blueink.py memory list      --brand "理想汽车" [--min-confidence 0.65]
python3 scripts/blueink.py memory add       --file <feedback.json>
python3 scripts/blueink.py memory confirm   --id M-2026-08-22-01
python3 scripts/blueink.py memory reinforce --id M-2026-08-22-01 --run <run_id> [--same-event]
python3 scripts/blueink.py memory counter   --id M-2026-08-22-01 --run <run_id> \
        --note "核心信息稿老师要求保留原始参数" [--narrow "核心信息"]
python3 scripts/blueink.py memory cancel    --id M-2026-08-22-01 --run <run_id>
python3 scripts/blueink.py memory retire    --id M-2026-08-22-01 --note "老师明确否定"
```

`--narrow` 是"缩小适用范围"的执行方式：它给旧结论追加一条不适用范围，同时记下反例。**优先用它，而不是让置信度一路降到失效**——降置信度只是让这条记忆变哑，缩范围才是把观察保留下来并说清它在哪里成立。

## 九 · 一条不能省的纪律

**单次修改绝不变成硬规则。**

一次临时口径、某位领导的个人偏好、赶时间的妥协，都可能被误学成长期规则。判不准归属时，归到更低的影响范围，不是更高的。

过拟合的代价远大于学得慢的代价：学得慢只是暂时没有帮上忙；过拟合会主动生成错的东西，而且老师要花更多时间去反复纠正同一条被错学的规则。

## 十 · 换领导、换品牌怎么办

- **换领导**：新增带生效日期的新证据，已有记忆不删。`trigger` 里加上 `publisher` 或时间范围，让先后两套偏好各自适用于各自的时间段。这样"换领导就要全部重来"的问题就不存在了——历史依然可查，只是不再默认适用。
- **品牌终止合作**：归档或删除该项目的 `.blueink/` 即可。通用方法论、其他品牌、六个角色一行不动。
- **新增品牌**：新建项目、绑定新的知识库目录。不改技能，不加规则文件。

## 十一 · 明示限制

- **`memory.json` 没有并发保护。** 两个进程同时写会丢掉一次更新。这是单人单机工具的取舍——加文件锁能防，但会给一个几乎不会发生的场景引入一套需要维护的机制。同时开两个终端改同一个品牌的记忆时，自己错开。
- **归因准确性无法机械校验。** 审计只能检查候选知识**带了**触发条件和反例、置信度没越界，检查不了归因归得对不对。归错的代价由置信度机制吸收：错的归因拿不到重复证据，会在半年后衰减掉；真的规律会反复被验证。
- **`learning/` 值得单独备份。** `index/` 可以随时重建，`runs/` 只是历史，但记忆是这位老师一段时间里积累的判断，删了不可恢复。

## 十二 · 退役的记忆去哪了

`memory retire` 不删记录，只把它标成退役——一条被反例推翻的观察仍然是观察，删掉它等于把"这里曾经踩过坑"这件事也一起删了。`memory list` 默认不显示退役项；要看它们用 `--include-retired`。

调查"这条偏好为什么突然不生效了"时先加这个参数：多半它没消失，是被某次反例退役了。
