# 交付契约

成稿后读这里。定义交付给文案老师的东西长什么样，以及什么不给他看。

## 一 · 先立一条判据

**审查报告没有天然价值。** 只有当它帮助文案老师决定"这稿现在能不能交、哪里必须处理"时，才值得存在。

一份罗列"通过了哪些规则、调用了哪些子智能体、读取了哪些文件"的长报告，业务老师大概率不看。而一旦他学会跳过它，后面所有的质量信息都失效了。

但完全没有审查结果也不行——老师明确提出需要"列明来源出处"，他要快速发现杜撰、事实缺口和口径风险。

所以需要的不是审查报告，而是**一张极短的交付前核对卡**加一份**实际来源清单**。

决策卡与交付内容的可复制骨架在 `assets/decision-card-template.md`，成稿前后各读一次即可。

## 二 · 交付物形态

业务侧只看到这些，顺序固定：

```
<正文>

交付前核对卡
<只列必须处理的问题，最多 3—5 条>

实际来源
<只列本稿真正用到的来源>
```

没有问题时，核对卡压缩成一句：

> 可进入人工初审。核心事实均有来源，未发现跨品牌信息和待确认事实。详见来源清单。

**同一份内容必须同时写入 `.blueink/runs/<run_id>/delivery.md`。** 这不是留档洁癖：没有它，事后无法区分"生成得不好"和"生成没问题但交付时漏了核对卡"——而这两种问题的处置完全不同。审计的输出有效一项会检查它存在、含结论行与来源清单，并且没有泄漏技术轨迹。

## 三 · 核对卡

### 结论行

固定三种，口径来自 `verify.json` 的 `verdict`，不允许主智能体自行放宽：

| 结论 | 触发条件 |
|---|---|
| 可进入人工初审 | 所有事实性表达均为 `matched`，无跨品牌、无红线命中 |
| 有待确认项 | 存在 `drifted` 或 `stale`，但无 `unsourced` / 跨品牌 / 红线 |
| 暂不建议提交 | 出现任一 `unsourced`、`cross_brand` 或 `redline_hits` |

### 问题条目

**只列未通过项。** 通过项一条都不写——写了就等于让老师在一堆"√"里找那个"×"。

每条四个要素，一行写完：

> 第 3 段「交付量逼近 4 万台」→ 来源原文为「超过 3.2 万台」（需求材料 P2，2026-06-11）→ 建议改回原文表述

要素依次是：**稿件原句（带段号）· 问题 · 来源 · 建议动作**。

超过 5 条时不要全列。按严重度排序取前 5 条，末尾加一行「另有 N 处待确认项，见后台核验记录」。**列 12 条等于没列**——老师会整体跳过。

### 事实来源覆盖

按段落或事实组映射，一行一组：

> 第 1—2 段（交付数据）：有来源 ｜ 第 3 段（产能规划）：有来源 ｜ 第 4 段（行业趋势）：无来源，属背景表述

**不在正文里密集插入引用符号。** 正文是交给客户的稿子，不是带脚注的报告。

## 四 · 实际来源清单

只列本稿真正用到的：**老师本次提供的附件**、需求材料、官方信息、历史稿件。来自 `verify.json` 的 `sources_used`。附件用老师给你的那个文件名，不要换成内部路径——他要能一眼认出这就是他给的那两份。

**不展示检索结果全集。** 证据研究员可能看了 20 份文件，最后用了 6 份，清单里就是 6 份。列 20 份会让老师无法判断哪份才是关键依据。

每条一行：来源类型 · 文件名或 URL · 日期。绝对路径不必列全，列到可辨识即可。

## 五 · A/B 呈现

保持极简。差异卡最多五行，不做长篇对比分析。

```
A稿｜推荐：从用户价值切入
<正文>

B稿｜备选：从技术突破切入
<正文>

差异
核心主线    A：交付节奏证明产品被认可      B：平台能力已过量产门槛
开篇切口    A：一位车主的提车时间          B：一条产线的良品率变化
信息重心    A：用户反馈与交付数据          B：技术路径与制造能力
更适合      A：面向大众媒体与用户沟通      B：面向行业媒体与投资者
主要代价    A：弱化了技术护城河            B：读者门槛更高

交付前核对卡
<两稿合并列，标明属于哪一稿>

实际来源
<两稿共用来源 + 各自新增来源>
```

三条纪律：

- **A/B 差异必须发生在主线、素材取舍或信息预算层面。** 只有措辞不同不算合格备选稿，出现这种情况应当在策略阶段就放弃 A/B。
- **长稿只在主线或结构真正不同时才出两篇全文。** 只是标题、导语或语义温度不同，就只给对应部分的 A/B，不重复整篇正文。
- **编辑反方不替老师选边。** 差异卡陈述各自的适合场景与代价；只有某一稿存在实质缺陷时才明确指出。

老师选 A 还是 B 会成为学习外循环最有价值的证据——系统由此知道他偏好哪个变量。

## 六 · 融合两稿的正确做法

老师说"A 的开头配 B 的中段"时，**不要直接拼句子**。两稿的主线不同，拼起来会互相打架：A 的开头承诺了一个论证方向，B 的中段在论证另一个。

正确做法：主智能体把老师选择的元素整理成第三份**融合写作程序**（明确融合后的主线、取舍和信息预算），再让写作子智能体生成最终稿。

## 七 · 不给业务侧看的东西

| 不展示 | 去哪里了 |
|---|---|
| 完整调用轨迹、子智能体名称 | `.blueink/runs/<run_id>/` |
| 各角色回执原文 | 同上 |
| 读过的文件与规则清单 | `evidence.json` 的 `read_paths` |
| 七个决策域的状态 | `interview.json` |
| 检索过但未使用的资料 | `evidence.json` 的 `discarded` |
| 已通过的检查项 | `verify.json` 的 `claims` |
| 长篇方法论说明 | 就在这些 references 里 |

**这不是隐藏信息，是分层。** 老师随时可以要求看后台记录，主智能体照给；但默认交付里塞进这些，会让真正需要处理的 3 条问题被埋掉。

## 八 · 第一版不承担的交付

正文默认以 Markdown 或纯文本呈现，可以直接复制进 Word。

不做：Word 排版、字体、配图、品牌文档模板、DOCX 渲染、客户端提交格式。这些属于"交付物生产"，不属于"文案生成方法论"。以后确有需求，做成独立的交付适配器，不改核心方法论和子智能体编排。
