# 编排协议

启动任何子智能体前读这里。这份文件定义主智能体如何调度六个角色、任务单与回执的字段契约、以及什么情况下要求返工。

## 一 · 调用图只有一层

```
                     文案老师
                        ↕
                    主智能体
        ┌───────┬───────┬───────┬───────┬───────┐
        ↓       ↓       ↓       ↓       ↓       ↓
     证据    编辑策略  专业   来源核验  编辑    反馈归因
     研究员   师(×1|2) 写作者   员      反方     员
```

**子智能体之间不互相调用，不互相看回执**（唯一例外：编辑策略师读证据研究员的回执，写作者读程序，核验员读证据与程序——都是主智能体显式在任务单里传给它们的，不是它们自己去拿的）。

这条约束的目的是防止"文件层层嵌套"变成"调用层层嵌套"。一层调用图意味着：任何一次失败，责任落在恰好一个角色上。

## 二 · 各角色的输入白名单

| 角色 | 允许的 inputs | 明确不给 |
|---|---|---|
| 证据研究员 | 任务单、`kb_root`、`skill_root`、`cli`、本次登记的附件 | — |
| 编辑策略师 | `evidence.json`、本次登记的附件 | 另一个策略师实例的回执、`kb_root` 的自主检索 |
| 专业写作者 | `program.json` + 程序 `authorized_reads` 里的文件 | `evidence.json` 全文、任何检索能力 |
| 来源核验员 | `draft.md`、`evidence.json`、`program.json` | `strategy.json`、`adversary.json` |
| 编辑反方 | `draft.md`、本次传播任务一句话、交付合同 | `strategy.json`、`program.json`、`verify.json` |
| 反馈归因员 | 系统初稿、老师修改稿或反馈原文、`program.json`、该品牌记忆库 | — |

**为什么策略师可以回读附件，写作者不可以。** 附件里常常同时装着事实和编辑方向（一份媒体指引可能给出五条竞争性写作主线），后者正是策略师要判断的东西，拦住它等于让它只能在研究员的摘要上做判断。但**事实一律以 `evidence.json` 为准**：研究员已经标出哪些数字不允许写、哪些口径存在冲突，策略师回读附件时不得越过这条线自行恢复被拦下的事实——那是"不补事实"这条禁令的核心。写作者不同：它的输入是已经定稿的 `program.json`，回读源文件等于在成稿阶段偷偷重做一次素材选择，而那会让取舍问题与表达问题永久混在一起。

两条容易被读成矛盾的地方，说清楚：

- **给核验员 `program.json`，不给 `strategy.json`——这不矛盾。** `program.json` 是**结论**（事实边界、主线、舍弃项），核验员必须知道边界才能核对；`strategy.json` 是**理由**，理由会说服它，让它替策略辩护。给结论不给理由，正是独立性的实现方式。
- **编辑反方连 `program.json` 也不给。** 它判断的是"这篇稿子的信息权重合不合理"，不是"它有没有照计划执行"。后者是 `write-receipt.json` 与 `program.json` 的逐项对照，由主智能体做。给了预算，反方就会变成一个合规检查器，而合规检查已经有人做了。

## 三 · 怎么启动一个子智能体

**默认路径：原生子智能体。** `subagent_type` 直接取角色名：

| 角色 | `subagent_type` | 工具白名单 |
|---|---|---|
| 证据研究员 | `blueink-evidence-researcher` | Read, Grep, Glob, Bash, WebFetch, WebSearch |
| 编辑策略师 | `blueink-editorial-strategist` | Read, Write |
| 专业写作者 | `blueink-professional-writer` | Read, Write |
| 来源核验员 | `blueink-source-verifier` | Read, Write |
| 编辑反方 | `blueink-editorial-adversary` | Read, Write |
| 反馈归因员 | `blueink-feedback-attributor` | Read, Write |

**为什么这是默认而不是可选。** 写作者、策略师、核验员、反方、归因员都**没有检索工具**，这是设计的一部分：写作阶段重新翻库等于在成稿时偷偷换了一次素材选择，核验员有搜索能力就会在发现某句话没依据时顺手找一个来源把它圆上。这些边界只有在原生注册时才由工具层强制执行。走 `general-purpose` 时它们全都拿到全套工具，边界退化成自律，只能靠审计 A4 事后发现——发现得到，但那时稿子已经写完了。

安装时 `./install.sh` 默认把六个角色注册到 `~/.claude/agents/`（插件形态由 `agents/` 目录自动注册）。

任务单直接作为 prompt 传给子智能体。**它是一份委托，不是一份答案。**

```
【任务单】
run_id: 20260822-143512-lixiang
task_id: T1
role: evidence-researcher
brand: 理想汽车
teacher: 张老师
kb_root: /Users/xxx/理想汽车知识库
skill_root: /Users/xxx/.claude/skills/blueink-suite
cli: python3 /Users/xxx/.claude/skills/blueink-suite/scripts/blueink.py --project /Users/xxx/项目
evidence_boundary: attachments
attachments:
  - /Users/xxx/附件/【指引】理想汽车2026年第一季度财报.md
  - /Users/xxx/附件/【新闻稿】理想汽车公布2026年第一季度财报.md
ask: 本次要为「2026 年一季度财报」写一篇 1500 字面向媒体的观点稿，需要可用事实、时间线与冲突
constraints:
  - 先只用 attachments 成稿所需的事实；这两份就是本次证据边界
  - 只有出现会阻止成稿的高影响缺口时，才用 cli retrieve 在 kb_root 内最小范围补，并写进 gaps
  - 联网前先跑 cli official check-url，退出码非 0 就标成缺口
expect: /Users/xxx/项目/.blueink/runs/20260822-143512-lixiang/evidence.json
```

**五条硬纪律。**

- **`skill_root` 是每个角色的必填项，不只是取证角色。** 角色需要读 references（策略师要读《品类任务边界》，写作者要读自己的契约）——没有 `skill_root`，它只能在项目目录里逐个猜路径。缺了它，一个策略师实例可能连试七个不存在的路径才放弃。**子智能体不知道技能装在哪，除非你告诉它。**
- **`cli` 必须给出可直接执行的绝对命令。** 子智能体的工作目录不保证与主智能体一致。不给 `cli`，取证角色只能自己去猜 `.blueink/index/index.json` 在哪，而那会浪费掉一整轮。同理 `expect` 必须是绝对路径，回执落地位置由主智能体决定，不由子智能体自选。
- **任务单不超过 20 行，`ask` 不超过 3 行。** 超出的部分几乎总是主智能体把自己的结论提前写了进去。
- **不预置结论。** `ask` 只说要解决什么问题，不说答案是什么。给编辑策略师的任务单里出现"建议以战略定力为主线"这类句子，独立判断就已经结束了——它会去论证你的结论，而你需要的是一个有可能反对你的判断。
- **`context` 只给必要的最小集。** 不要把整轮访谈记录倒给子智能体。尤其是来源核验员和编辑反方，**绝不能把 `strategy.json` 的理由传给它们**。

**有附件时，附件优先写进任务单，而不是让子智能体自己去发现。** `evidence_boundary: attachments` 是一条声明：先只用附件；真的缺到无法成稿时才最小范围查库，并把缺口写进 `gaps`。**不为"可能有用的风格参考"展开整库研究**——那不是更严谨，那是把一个附件驱动的任务变成一次知识库普查。

**退化路径（未注册成原生子智能体时）：** `subagent_type` 取 `general-purpose`，prompt 第一行固定为读取角色契约的指令，第二段才是任务单：

```
先读取并严格遵守 <技能根目录>/agents/evidence-researcher.md，把它当作你的完整角色定义。
读完后执行下面的任务单，不要执行任务单之外的任何动作。
```

## 四 · 回执信封

每份回执都必须带这五个字段，之后才是角色特有内容：

```json
{"role": "...", "run_id": "...", "task_id": "...", "status": "...", "read_paths": []}
```

每份回执都要写 `read_paths`——**包括正常情况下应为空数组的角色**。空数组是一个断言（"我没有打开任何文件"），缺这个字段则什么都没断言，审计无法区分"没读"和"读了没说"。

**`read_paths` 里的每条路径必须是绝对路径，或是相对 `kb_root` 的路径——不许缩写。** 把 `/Users/…/知识库/【整理后】…` 写成 `【整理后】…` 会掐掉前缀：读的文件是对的，但**写下来的那条路径没人能解析**，于是这条来源事后无法复核——而“来源可复核”就是核验员存在的全部理由。审计会把它报成“声称读过但文件不存在”，并指出路径不完整。缩写只允许出现在交付给老师的来源清单里（那里的读者是人），不许出现在回执里。

**回执必须能落得下来。** 一个取证角色可以反复宣布"信息足够、准备写 evidence.json"，然后连续数分钟不产出任何文件，最后一份回执都没有。写审计材料本身成了主要耗时，那比不记账更糟——同时花掉了时间，又没换来可定位性。

所以回执有体量上限，超出的内容不属于回执：

| 回执 | 最小必要内容 | 上限 |
|---|---|---|
| `evidence.json` | `facts`（每条带 `source` / `source_date`）、`timeline`、`conflicts`、`gaps`、`read_paths` | facts ≤ 25 条；每条 `claim` ≤ 2 行；不复制原文段落，只写结论与来源路径 |
| `strategy.json` | `recommended_line`（claim + why）、`alternative_line`（有才写）、`material_plan`（foreground / discarded）、`information_budget` | ≤ 220 行；`why` ≤ 5 行 |
| `program.json` | `authorized_reads`、`material_plan.discarded`、`assumptions`、主线、信息预算 | ≤ 120 行 |
| `write-receipt.json` | `read_paths`、`style_refs_used`、`deviations`、`missing_facts` | ≤ 40 行 |
| `verify.json` | `claims`（逐句判定）、`coverage`、`cross_brand`、`redline_hits` | 只列有问题的句子；全部通过时 `claims` 可为空并在 `coverage` 里给计数 |
| `adversary.json` | `attacks`（每条：攻击点 · 为什么成立 · 严重度）、`missed_stronger_line` | ≤ 6 条攻击，按严重度排序 |
| `feedback.json` | 四级候选记忆，每条带 `trigger` / `not_applicable` / `confidence` / `evidence_strength` | ≤ 8 条候选 |

**超限时的正确动作是舍弃，不是压缩字号。** 一份 40 条事实的证据回执说明取证没有做取舍——而取舍本来就是它的工作。

**这些数字是实测出来的，不是拍的。** 一条真实任务（两份附件共 32KB、六组口径冲突、两条实质竞争主线）实际落出 `evidence.json` 24 条事实约 450 行、`strategy.json` 约 214 行。上表里的上限按这个量级取，留了余量。**这一点很重要：一个达不到的上限等于没有上限**——它只会被忽略，而被忽略的约束比不存在的约束更糟，因为它让人以为这件事已经被管住了。真的觉得某个上限拦住了必要内容时，先确认那些内容属于回执（用于裁决和定位）还是属于本该被舍弃的过程材料。

`status` 的通用口径：

| status | 含义 | 主智能体该做什么 |
|---|---|---|
| `ok` / `pass` / `sound` | 正常完成 | 进入下一步 |
| `partial` | 完成但有缺口 | 判断缺口是否高影响；高影响则回访谈 |
| `objected` | 角色对上游判断有实质异议 | 读异议，决定返工还是驳回（驳回要写理由） |
| `must_fix` / `weak` | 发现必须处理的问题 | 局部返工 |
| `broken` | 方向性问题 | 退回编辑策略阶段 |
| `blocked` | 缺关键输入，无法开工 | 补输入，不许让它硬写 |

**`blocked` 不许绕过。** 让一个 blocked 的角色"先写个大概"，产出的是一份看起来完整、实际缺料的东西——这是最常见的一类失败形态。

## 五 · 标准流程

```
0  运行开启      blueink.py open       → run_id、启动回执行
1  访谈          主智能体 ↔ 老师            → interview.json（每轮追加）
2  取证          证据研究员                 → evidence.json
   ↳ 冲突或高影响缺口 → 回 1 追问，不自己选边
3  编辑策略      编辑策略师（必要时 ×2）     → strategy.json [, strategy-b.json]
   ↳ needs_evidence 且高影响 → 回 2
   ↳ status: blocked → 回 1
4  写作程序      主智能体合成               → program.json
   ↳ 有新增高影响判断 → 展示决策卡（decision-card.md），等确认
   ↳ 无新增 → 两三句收敛陈述，直接进 5
5  成稿          专业写作者（A/B 时 ×2）     → draft.md [, draft-a/b.md] + write-receipt
   ↳ status: objected → 回 3
   ↳ missing_facts 非空 → 回 2 或问老师，不许近似值
6  来源核验      来源核验员（每稿一次）      → verify.json
   ↳ unsourced / cross_brand / redline_hits → 回 5 定点重写该句
7  编辑反方      编辑反方                   → adversary.json
   ↳ broken → 回 3
   ↳ weak   → 回 5
8  交付          主智能体                   → 正文 + 核对卡 + 来源清单，同时写 delivery.md
9  运行归档      blueink.py close      → 写入 index.json 摘要
──  以下只在老师给出反馈后 ──
10 反馈归因      反馈归因员                 → feedback.json
11 记忆晋级      主智能体按判据             → .blueink/learning/
```

**这不是七个必须逐项执行的步骤。** 它是一条有向主干，允许三种动态行为：**已有可靠结果的节点跳过**（老师已经说清的不再问，附件已经给足的不再检索，上一轮已落盘的回执不再重跑）；**条件分支只在真的出现时效、冲突、竞争主线或高影响推断时触发**；**发现问题只局部回退**——事实问题回 2，主线问题回 3，执行偏差回 5，不重跑整条链。**不要为这几个节点向老师输出状态表或进度表。**

**回执落盘是断点，所以产回执的调用一律放前台。** 这一条不只针对取证。两种形态一样的失败：

- 第一次是取证放后台，跑满运行时的等待上限被终止，`evidence.json` 没落盘，下一轮只能从头重跑一次完整取证。
- 第二次是两个策略师实例并行放后台，同样跑满上限被终止，`strategy.json` 一份都没有——而这一次取证已经落盘了，所以只丢了策略这一段。

规则因此是通用的：**任何会产出回执的子智能体调用都放前台**，回执落盘之后才启动下一个角色。需要两个互相隔离的实例时（A/B 主线），**前台顺序跑两次**，不要并行放后台——隔离要求的是上下文互不可见，不是并发。顺序跑慢一点，但每一段都有断点；并行跑快一点，代价是被打断时两段一起作废。

**没有断点的长任务被打断就等于全部作废。** 这比慢更贵。

**第 5 节流程里第 4 步有三个字段必须写满，漏了会让审计器持续误报，而误报会让人学会忽略它：**

| 字段 | 漏了会怎样 |
|---|---|
| `authorized_reads` | 写作者读的每个文件都会被判为越权。这个清单通常就是本次选定的风格样本路径 |
| `material_plan.discarded` | 核验员无法判断写作阶段有没有重新选素材 |
| `assumptions` | 决策卡该不该暂停失去判据 |

完整字段见 `assets/writing-program.schema.json`。

**第 8 步的 `delivery.md` 不是可选项。** 它记录业务侧实际收到了什么——没有它，事后无法区分"生成得不好"和"生成没问题但交付时漏了核对卡"。

**第 6 和 7 在逻辑上互不依赖**：核验员和反方都只读 `draft.md`。但它们各自产回执，所以仍然前台顺序跑——省一轮往返换来的是被打断时两份回执一起作废。

**只有 4 是可能暂停的点。** 其余步骤之间不要向老师汇报进度——"正在调用证据研究员"这类播报对老师毫无价值，只会稀释真正需要他决策的那一次提问。

`blueink.py stage` 是可选的。`doctor` 会按产出文件反推运行走到了哪一步，所以不标记阶段不会丢失定位能力；标记只是让"标记阶段"与"实际产出"能互相对照，从而发现某个角色没落回执。

## 六 · 边界：本技能不承担改稿编排

生成过程内部当然会回退——第五节那些 `↳` 就是回退，它们由**回执 `status` 驱动**：
核验员报 `unsourced` 就回第 5 步定点重写，反方报 `broken` 就回第 3 步。这是生成内
循环，责任明确、终点确定。

**但"老师看完稿子提了修改意见，接下来退到哪一层"不由本技能负责。**

这条边界是会话里被反复确认过的：反复改稿要不要重跑链路、要不要做层级回退，这些
这个技能只负责文案生成。

所以这里**没有**一张"修改意见性质 → 退到第几步"的对照表，也**没有** `rework`
这类阶段回退命令。给出这张表就等于开始建设一个改稿操作系统：它需要版本、需要
diff、需要知道哪一段是上一轮哪个判断的产物，而这三样本技能一样都没有。半个改稿
系统比没有更糟——它会让人以为改稿这件事已经被管起来了。

老师的修改意见只有一个去处：**学习外循环**（第五节第 10、11 步）。反馈归因员把它
归因成带置信度的条件化记忆，下一次生成时按置信度参与写作程序。这是"下次做得更
对"，不是"这次退回去重做"。要基于修改意见再出一稿，就正常发起下一次生成，让已经
沉淀的记忆去发挥作用。

`self_check.py --claims` 机械守着这条边界：子命令表里一旦出现 `rework` /
`rollback` / `revert` 这类名字就判失败，并且每个子命令都必须在文档里出现过——
范围失控从来不是一次大动作，是一次加一个子命令。

## 七 · 两个策略师实例

只在证据能支持两条**实质竞争**主线时启动第二个实例。

- 两个实例的任务单相同，`instance` 分别为 `a` 和 `b`。
- 两个实例**互相不可见**，也不要在任务单里提示"另一个实例会写什么"。
- **前台顺序跑两次，不要并行放后台。** 隔离要求的是上下文互不可见，不是并发；并行放后台一旦撞上运行时的等待上限，两份回执一起作废。
- 主智能体比对两份回执：如果 `recommended_line.claim` 实质相同（只是措辞不同），说明这不是真的两条路线——放弃 A/B，用其中较强的一份继续。

同理，A/B 写作的两个写作者实例共用同一 `evidence.json` 与同一事实边界，**不允许各自补不同的事实**。它们的差异只能来自 `program.json` 里的主线、取舍和信息预算。

## 八 · 运行记录

一次运行的完整目录：

```
.blueink/runs/<run_id>/
├── meta.json           品牌、模式、开始与结束时间
├── interview.json      逐轮访谈
├── retrievals.json     每次 retrieve --run 的候选清单与命中理由
├── evidence.json       证据研究员回执
├── strategy.json       编辑策略师回执（第二实例 strategy-b.json）
├── program.json        本次写作程序
├── decision-card.md    条件触发时展示给老师的决策卡
├── draft.md            正文（A/B 时 draft-a.md / draft-b.md）
├── write-receipt.json  写作者执行回执
├── verify.json         来源核验员回执
├── adversary.json      编辑反方回执
├── delivery.md         交付给老师的最终内容（必写）
└── feedback.json       反馈归因员回执（仅在有反馈时）
```

**这些文件业务侧永远看不到。** 它们只在定位问题时被读取。老师看到的只有正文、必要时的极短核对卡和实际来源清单。

**它们也不永久保留。** 运行目录里躺着访谈原文、素材路径和交付正文——它是可定位性的载体，同时也是一份会无限增长的客户内容留存。留存期是一条显式策略而不是"永远不删"：默认保留 90 天，且无论多旧至少保留最近 20 次运行。次数这一条是必要的，一个几个月才写一稿的老师纯按时间清会被清空，而那正是他定位问题时唯一的依据。

```bash
python3 scripts/blueink.py open --mode 生成          # 品牌取自工作空间，不用也不能在这里传
python3 scripts/blueink.py close --run <run_id>
python3 scripts/blueink.py audit --input .blueink/runs/<run_id> --output /tmp/verdict.json
python3 scripts/blueink.py purge                     # 试运行：打印将删除哪些旧运行
python3 scripts/blueink.py purge --apply             # 真的删
```

`purge` 默认试运行。删除范围只到项目内 `.blueink/runs/<run_id>/` 这一层派生物，**永不触及源知识库**——源库只读是本技能最硬的一条承诺，清理留存不是它的例外。

审计器把六项验收契约变成机械检查。**每次运行结束都跑一次 audit**，它比人眼更早发现"写作者其实重新扫了库""访谈其实是问卷""来源其实没覆盖"。
